# 旅行用割り勘アプリ 仕様書

この文書には、ユーザーと相談して確定した仕様を記録します。
未決定事項は、決定するまで実装上の前提にしません。

## 確定した仕様

### 費用負担と端数処理

- 国内旅行の入力金額と最終的な負担額は、1円単位の整数として扱う。
- 支払いごとに、その費用を負担するメンバーを1人以上指定する。
- 支払いごとの理論負担額は、支払額を指定された負担者数で均等に割って求める。この段階では1円単位に丸めない。
- 各メンバーの理論負担額を旅行内の全支払いについて合計してから、最後に一度だけ端数処理を行う。
- 最初に各メンバーの理論負担額の合計を1円未満切り捨てる。
- 切り捨て後に余った円は、理論負担額の小数部分が大きいメンバーから1円ずつ割り当てる。
- 小数部分も同じ場合は、旅行への登録順が早いメンバーから割り当てる。

例として、10,001円を3人で割る場合は次の負担額になる。

- 登録順1人目：3,334円
- 登録順2人目：3,334円
- 登録順3人目：3,333円

この方法を採用する理由は次のとおり。

- 全員の負担額の合計と総費用が必ず一致する。
- 同じ入力なら毎回同じ結果になり、動作を説明しやすい。
- 各メンバーの最終負担額と理論負担額の差を1円未満に抑えられる。
- 支払いのたびに同じメンバーへ端数が加算される偏りを防げる。

例えば、100円を3人全員で負担する支払いが3回ある場合、支払いごとに丸めると登録順1人目が毎回34円を負担し、合計102円になる可能性がある。本仕様では丸める前の理論負担額を先に合計するため、3人とも100円の負担になる。

実装ではJavaScriptの小数計算による誤差を避けるため、途中の理論負担額を正確な分数として計算し、最後に整数へ変換する。

ここで決めるのは各参加者の最終的な負担額である。
実際に誰が誰へ送金するかは、それまでに各参加者が支払った金額との差から別途計算する。

### データ保存と旅行履歴

- DBは使用せず、ブラウザーの `localStorage` に保存する。
- ページを再読み込みした後やブラウザーを閉じた後も、同じ端末・同じブラウザーではデータを復元できるようにする。
- 複数の旅行データを保存できるようにする。
- 新しい旅行データを作成できるようにする。
- 過去の旅行を一覧表示し、選択して内容を確認・編集できるようにする。
- 特定の旅行だけを削除できるようにする。
- 保存されている全旅行データを削除できるようにする。
- 個別削除と全削除の前には確認画面を表示し、誤操作を防止する。

`localStorage` を採用する理由は次のとおり。

- DBを用意せず、課題の条件内でデータを保持できる。
- 誤って再読み込みやブラウザー終了をしても、入力内容を復元できる。
- 旅行履歴を残せるため、同じアプリを複数回の旅行で利用できる。

次の制約をユーザーに分かる形で扱う。

- データは保存した端末とブラウザー内だけで利用できる。
- 別の端末との同期や複数人での共有は行わない。
- ブラウザーのサイトデータを削除すると旅行履歴も消える。

実装は、国内旅行の必須機能を完成させた後に旅行履歴機能を追加する順番とする。

### データ構成

`localStorage` に保存するデータは、次の構成とする。

- アプリ全体：データ形式のバージョン、旅行一覧
- 旅行：一意なID、旅行名、メンバー一覧、支払い一覧
- メンバー：一意なID、名前
- 支払い：一意なID、支払者ID、金額、通貨コード、内容、費用を負担するメンバーID一覧

メンバー名ではなくIDで支払者や負担者を関連付ける。これにより、将来メンバー名を変更しても支払いとの関係が壊れないようにする。メンバー一覧の配列順を登録順として扱い、端数処理などの同点時に使用する。

金額は通貨ごとの最小単位による整数で保存する。例えば、1,200円は `1200`、12.34米ドルは1,234セントとして `1234` を保存する。通貨コードは `JPY` や `USD` のような値を別に保存する。小数のまま保存しないことで、JavaScriptの小数計算による誤差を避ける。

旅行の作成日時と更新日時は保存しない。旅行一覧の配列順を作成順として扱い、新しく作成した旅行を配列の先頭へ追加する。ホーム画面では、新しく作成した旅行から順番に表示する。旅行を編集しても一覧の順番は変更しない。

総費用、各メンバーの負担額、差額、送金結果など、元の入力から求められる値は保存しない。画面表示時に旅行・メンバー・支払いから毎回計算し、支払いの追加や削除後に古い計算結果が残ることを防ぐ。

データ形式にはバージョン番号を付ける。後から項目を追加した場合に、保存済みデータの形式を判別できるようにするためである。

### 画面構成

アプリは、役割の異なる次の2画面で構成する。

#### ホーム画面（`/`）

- 新しい旅行を作成する。
- 保存されている過去の旅行を一覧表示する。
- 過去の旅行を選択して旅行詳細画面へ移動する。
- 特定の旅行を削除する。
- 全旅行データを削除する。

新しい旅行の作成フォームは、次の仕様とする。

- 旅行名を必須入力とする。
- 日付は入力項目に含めない。
- メンバーを2人以上必須とする。
- 最初から2人分の名前入力欄を表示する。
- 「メンバーを追加」操作で、3人目以降の入力欄を増やせるようにする。
- 空白だけの旅行名やメンバー名は登録できないようにする。
- 同じ旅行内で重複するメンバー名は登録できないようにする。
- 旅行の作成後も、旅行詳細画面からメンバーを追加できるようにする。

旅行の作成時点で2人以上のメンバーを必須にすることで、参加者がいない空の旅行が保存されることを防ぎ、作成後すぐに支払いを登録できるようにする。日付は割り勘計算に必要ないため入力項目を増やさず、操作を簡潔に保つ。

#### 旅行詳細画面（`/trips/[tripId]`）

- 選択中の旅行名など、旅行の情報を表示する。
- 参加者を追加・表示する。
- 支払いを追加・表示する。
- 総費用と精算結果を表示する。
- ホーム画面へ戻れるようにする。

### メンバーの追加と削除

- 旅行には常に2人以上のメンバーが残るようにする。
- メンバーが2人しかいない場合は、どちらのメンバーも削除できないようにする。
- 削除対象のメンバーが「支払った人」または「費用を負担する人」として含まれる支払いが1件でもある場合は、削除できないようにする。
- 削除できない場合は、その理由と必要な操作を画面に表示する。支払い記録がある場合は、該当する支払いを先に削除するよう案内する。
- 削除可能な場合も、実行前に確認画面を表示する。
- メンバーを追加または削除した後は、登録されている支払いと各支払いの負担者をもとに精算結果を再計算する。
- 支払いの登録後に新しいメンバーを追加しても、そのメンバーを既存の支払いの負担者には自動追加しない。
- メンバー追加後に新しく登録する支払いでは、追加したメンバーを含む現在の全メンバーを負担者として初期選択する。

支払いに含まれるメンバーの削除を禁止するのは、支払った人や費用の負担者が存在しない不整合なデータが残ることを防ぐためである。追加したメンバーを既存の支払いへ自動追加しないのは、途中参加した人が参加前の費用まで意図せず負担することを防ぎ、過去の入力内容を維持するためである。

### 支払いの入力と削除

支払いの追加フォームは、次の4項目をすべて必須とする。

- 支払った人：旅行に登録されているメンバーから選択する。
- 金額：1円以上の整数を入力する。
- 内容：何に支払ったかを入力する（例：宿泊費、レンタカー代）。
- この費用を負担する人：旅行に登録されているメンバーから1人以上を選択する。初期状態では全メンバーを選択する。

支払った人と費用を負担する人は一致しなくてもよい。例えば、りさがさきの食事代1,200円を立て替えた場合は、「支払った人」をりさ、「この費用を負担する人」をさきだけにする。これにより、精算結果へ「さきからりさへ1,200円」を反映できる。

入力値は次のルールで検証する。

- 金額の空欄、0円、マイナス金額、小数は登録できないようにする。
- 金額入力欄に `min=1` と `step=1` を指定し、TypeScriptの処理でも同じ条件を検証する。
- 内容の空欄や空白だけの入力は登録できないようにする。
- 内容の前後にある不要な空白は登録時に取り除く。
- 費用を負担する人が1人も選択されていない場合は登録できないようにする。

入力欄の制約に加えてTypeScriptでも検証する理由は、HTMLの入力制限だけでは不正な値を完全には防げないためである。また、日本円を整数で保持することで、小数による計算誤差を避け、確定済みの1円単位の端数処理を適用しやすくする。

登録済みの支払いは削除できるようにし、誤操作を防ぐため、削除前に確認画面を表示する。支払いの編集機能は、国内旅行の基本機能が完成した後に追加する。

### 精算方法と表示

各メンバーについて、実際に支払った合計額から最終負担額を引いて差額を求める。

- 差額がプラスのメンバーは、お金を受け取る側とする。
- 差額がマイナスのメンバーは、お金を払う側とする。
- 差額が0円のメンバーは、送金の組み合わせに含めない。
- 払う金額と受け取る金額が大きいメンバー同士から順番に組み合わせる。
- 1回の送金額は、払う側の残額と受け取る側の残額のうち、小さい方とする。
- 同額の場合は、旅行への登録順が早いメンバーを先に処理する。
- 全員の差額が0円の場合は、「精算する必要はありません」と表示する。

精算結果は、「さきさんから、りささんへ 5,000円」のように、送金元・送金先・金額が一目で分かる形で表示する。この方法では、送金回数を参加人数から1を引いた回数以下に抑えられ、同じ入力から常に同じ結果を得られる。

この方法は、計算の速さ、実装の分かりやすさ、テストのしやすさを優先する。数学的に必ず最少の送金回数となる組み合わせを探索する機能は、国内旅行の基本機能が完成した後の追加候補とする。どちらの方法でも各メンバーが最終的に払う金額・受け取る金額は同じであり、違うのは送金の経路と回数である。

2画面に分ける理由は次のとおり。

- 旅行の選択・管理と、1つの旅行内で行う割り勘操作を分けられる。
- 1画面に情報を詰め込みすぎず、ユーザーが現在の操作を理解しやすい。
- Next.js App Routerのページ単位で役割を分けられるため、コードの責務も整理しやすい。
